# Работа над SMLT

Репозиторий содержит публичное Vue приложение, Go API и исходники отдельных приложений SMLT Max/Chat. Перед изменением определите, какой компонент владеет поведением, и сохраняйте его существующие границы.

## Рабочий процесс

1. Создайте ветку для задачи: `git switch -c feature/короткое-название`.
2. Изучите связанные компоненты и API контракт. Не меняйте frontend и backend несогласованно.
3. Для frontend установите зависимости строго по lockfile и соберите приложение:

   ```bash
   cd frontend
   corepack pnpm install --frozen-lockfile
   corepack pnpm run build
   ```

4. Для Go изменений выполните проверки из корня репозитория. Корневой
   `go.work` подключает `backend/`, поэтому используйте путь `./backend/...`:

   ```bash
   cd ..
   go test ./backend/...
   go vet ./backend/...
   ```

5. Для messenger используйте его отдельную инструкцию и только временную тестовую базу.
6. Проверьте `git diff`, не добавляйте сгенерированные `frontend-build/`, `node_modules`, локальные настройки или runtime файлы.
7. Откройте Pull Request в `main`, указав поведение, затронутые части и выполненные проверки.

## Структура

- `frontend/src/` — интерфейс и маршруты smlt.lol; `frontend/public/` — PWA и статические ресурсы.
- `backend/` — Go API, PostgreSQL доступ, администрирование и синхронизация Demonlist.
- `messenger/` — самостоятельные SMLT Max и Chat приложения и Python API.

## Безопасность и данные

- Никогда не коммитьте `.env`, пароли, токены, приватные ключи, production данные или конфигурации серверов.
- `backend/.env.example` — только имена и безопасные заглушки переменных; поддерживайте его без действительных секретов.
- Не запускайте миграции, seed/reset, админские запросы, синхронизацию или тесты против production базы.
- Административные API должны сохранять авторизацию, разрешённые HTTP методы, валидацию, ограничения размера тела и rate limits.
- Не добавляйте стороннюю аналитику, удалённые скрипты или новые внешние API без согласования с владельцем.
- Не публикуйте импортированные базовые прохождения демонов как новые события; сохраняйте правила baseline синхронизации и фильтр истории.
- Изменения кода не означают выкладку. Production build, restart служб, nginx и база обслуживаются отдельной процедурой после review владельцем.

Правила проекта и проверенные production пути находятся в `AGENTS.md` на VPS. При расхождении описаний сначала сверяйте фактическое состояние и обновляйте документацию только подтверждёнными сведениями.
